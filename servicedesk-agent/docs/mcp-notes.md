# MCP 架构笔记：什么时候值得上一个协议

> 本文是 2.2 的交付物。它不谈 API 细节（那是 2.3–2.7 的事），只回答一个问题：
> **我这个能力，该写成普通函数，还是写成 MCP Server？**

---

## 1. 先看一个数字：M×N 的适配器地狱

假设公司有 **M 个 AI 应用**（客服助手、工单机器人、内部 CLI、IDE 插件……），
要接 **N 个内部系统**（资产库、权限系统、工单系统、CMDB、监控……）。

### 做法一：每个应用自己写适配

```
客服助手 ──┬── 资产 API 适配
           ├── 权限 API 适配
           └── 工单 API 适配

工单机器人 ─┬── 资产 API 适配      ← 同一份逻辑，第二份实现
            ├── 权限 API 适配
            └── 工单 API 适配
```

适配器数量 = **M × N**。

而且要命的不只是数量，是**每份实现都会独立漂移**：客服助手那版会重试、机器人那版不会；
一个修了分页 bug，另一个没修。**M 越大，同一个 bug 就被复制 M 次。**

### 做法二：统一协议

```
客服助手 ──┐                    ┌── 资产 MCP Server
工单机器人 ─┼── MCP Client ─────┼── 权限 MCP Server
内部 CLI  ──┘                    └── 工单 MCP Server
```

适配器数量 = **M + N**（M 个 client 复用同一套协议，N 个 server 各自实现一次）。

### 什么时候真的划算

| M | N | 各自定制 | 统一协议 | 结论 |
|---|---|---|---|---|
| 1 | 5 | 5 | 6 | ❌ 协议反而更贵 |
| 2 | 2 | 4 | 4 | ⚖️ 打平（还要算协议学习成本，实际略亏） |
| 3 | 2 | 6 | 5 | ✅ 开始划算 |
| 3 | 5 | 15 | 8 | ✅ 明显划算 |
| 5 | 5 | 25 | 10 | ✅ 强烈建议 |

**判据：`M * N > M + N + 协议成本` 才划算。** 取 `协议成本 = 1`（一次性的规范学习与调试），
那么 `M ≥ 3 且 N ≥ 2`，或 `M ≥ 2 且 N ≥ 3`，才是明确的收益区。

> **一句话**：MCP 不是"更高级的 function calling"，它是**一个针对 M×N 问题的收敛手段**。
> 只有 M 或 N 大于 1 时，它才有存在意义。

## 2. 三个角色：Host / Client / Server

MCP 把"谁在用什么"拆成三层，这个拆分是整个协议的地基。

| 角色 | 是什么 | 例子 | 谁实现 |
|---|---|---|---|
| **Host** | 面向用户的宿主应用，拥有 UI 与最终决策权 | Claude Desktop、Cursor、你的客服助手 | 你 |
| **Client** | Host 内部为**每个 Server** 建立的一条连接 | 一个 Host 里可能有 5 个 client | 协议层/SDK |
| **Server** | 暴露能力的一方，只管"我能提供什么" | 资产查询服务、工单服务 | 你（或第三方） |

### 关键理解：Client 是"每个 Server 一个"

```
┌─────────────── Host（你的应用）───────────────┐
│                                               │
│  Client A ──► Server 资产（远程）              │
│  Client B ──► Server 工单（远程）              │
│  Client C ──► Server 文件（本地进程）          │
│                                               │
│  ↑ 三个 client，各自独立握手、独立鉴权          │
│  ↑ 但都共享 Host 的模型上下文与用户授权         │
└───────────────────────────────────────────────┘
```

**为什么不是"一个 client 连所有 server"**：因为每个 server 的版本、能力、鉴权方式、
生命周期都不同。拆成独立连接后，一个 server 挂了不影响其他；一个 server 升级协议不影响其他。

### 和 2.1 的关系

| | 2.1 的 Function Calling | MCP |
|---|---|---|
| 工具在哪 | **你的进程内** | **另一个进程/另一台机器** |
| 谁定义 schema | 你（pydantic） | Server（协议传输） |
| 谁执行 | 你的函数 | Server |
| 换工具要做什么 | 改代码、重新部署 | 改 Server，Host 不用动 |
| 适合 | 本项目自用的少量工具 | 跨应用、跨团队复用的能力 |

**所以：MCP 是"把工具从进程内搬到进程外"的那一层。** 2.1 学的一切（schema、参数校验、
错误字符串）在 MCP 里依然成立，只是多了网络边界。

## 3. 三种原语：Tools / Resources / Prompts

MCP Server 能暴露三种东西，**边界必须划清楚**，否则会做出一堆难用的 Server。

| 原语 | 本质 | 谁发起 | 模型能"决定"用吗 | 典型例子 |
|---|---|---|---|---|
| **Tools** | **动作**，可能有副作用 | 模型 | ✅ 能，且会带参数 | 查资产、建工单、发消息 |
| **Resources** | **数据**，只读，按 URI 定位 | 应用/用户 | ❌ 不能，由 Host 决定挂载什么 | `file:///docs/vpn.md`、`asset://NB-1024` |
| **Prompts** | **预置的提示模板**，带参数 | 用户 | ❌ 不能，由用户主动选择 | "解释这个告警"模板 |

### 判断口诀

- **"会不会改变状态？"** 会 → Tools。不会，但内容可能很大、需要按标识寻址 → Resources。
- **"是谁决定要不要用它？"** 模型 → Tools。应用 → Resources。用户 → Prompts。

### 三个常见误用

**误用 1：把只读数据做成 Tools。**

```
❌ get_document(doc_id) → 返回全文
✅ Resource: doc://vpn-guide，Host 按需挂载
```

原因：只读数据做成 Tool，模型每次都要"决定去读"，既费 token 又不可控。
做成 Resource，Host 可以预先知道有哪些数据可用，也能做缓存与权限控制。

**误用 2：把有副作用的动作做成 Resources。**

`Resource` 的语义是"可以安全地反复读"。如果你把"创建工单"做成 Resource，
任何一次预取、重试、渲染都会建一个新工单。

**误用 3：用 Prompts 传递业务逻辑。**

Prompts 是"给用户点的菜"，不是"给你的程序调用的函数"。业务逻辑放 Prompts 里，
等于把规则写在 UI 文案里。

## 4. 决策四问

用这四个问题判断"该不该 MCP 化"。**四个里有一个是"否"，就不该。**

### 问 1：这个能力会被**多个**消费方使用吗？

- 只有一个应用用 → **别做 MCP**，写个普通函数最快
- 已有 2 个以上应用在重复实现 → 该做

### 问 2：它需要**独立**的部署 / 升级 / 鉴权吗？

- 需要单独扩容、单独发版、单独授权 → 该做
- 和主应用同生共死 → 不必

### 问 3：会被**第三方**或**跨语言**客户端调用吗？

- 合作方、其他部门的系统要接 → 必须用协议
- 只有你们自己的 Python 代码 → 不必

### 问 4：`M × N > M + N + 1` 吗？

算出适配器数量对比。不划算就先别做——**先写函数，等第二个消费方出现时再抽象**。

> **反面模式：为"将来可能复用"提前做 MCP。**
> 你会在没有第二个消费者的情况下，为一个不存在的 M×N 问题付出协议成本。
> **正确的顺序是：先写函数 → 出现第二个消费方 → 抽成 MCP。**

## 5. 三个真实场景的判断

### 场景 A：工单查询

- 消费方：客服助手、工单机器人、内部 CLI（M=3）
- 后端系统：工单系统、资产系统（N=2）
- 需要独立鉴权（不同角色看到不同字段）：是
- 第三方：暂无

**判断：该做 MCP。** `3×2=6 > 3+2+1=6`？打平。但加上"鉴权需要独立"这条，倾向做。
（这正是那条阈值的边界感——纯算数是打平，业务权重把它推向"做"。）

### 场景 B：格式化日期

- 消费方：只有工单助手（M=1）
- 后端系统：无（纯函数，N=0）
- 需要独立部署：否
- 第三方：否

**判断：不该做。** 写个普通函数，`M×N` 根本构不成问题。
把它做成 MCP Server 只会多一个进程、一次网络往返、一套鉴权。

### 场景 C：资产只读查询，要给合作方访问

- 消费方：内部助手 + 合作方的运维平台（M=2，且**跨组织**）
- 后端系统：资产库（N=1）
- 需要独立鉴权：**是**（合作方只能看自己的设备）
- 第三方：**是**

**判断：该做。** 注意这里的理由**不是** `M×N`（`2×1=2 < 4`），
而是"跨组织 + 独立鉴权"——**协议是唯一能让外部方安全接入的方式**。

> 这条最能说明问题：**决策四问里，算数是必要条件，不是充分条件。**

---

## 6. 该怎么做（顺序很重要）

1. **先写普通函数**，把业务逻辑、参数校验、错误语义都跑通（2.1 已经做了）
2. **观察是否出现第二个消费方**（而不是预测）
3. 出现后，把函数包装成 MCP Server（2.4 开始）
4. Host 侧用 `langchain-mcp-adapters` 接回来（2.7）

**为什么这个顺序**：MCP 的协议细节（无状态、版本协商、订阅、鉴权）会吃掉你大量时间，
而**业务逻辑的正确性才是难点**。先把难点解决，再用协议把它暴露出去。

## 8. 一页速查

| 问题 | 答案 |
|---|---|
| MCP 解决什么 | M 个应用 × N 个系统的适配器重复 |
| 什么时候划算 | `M×N > M+N+1`，且至少一个业务理由（隔离/鉴权/跨组织） |
| 三个角色 | Host（宿主持有 UI）/ Client（每个 Server 一条）/ Server（暴露能力） |

| 最常见的错误 | 只有一个消费方就上 MCP |
