## 1. 为什么需要它（痛点先行）

上线前最常见的对话：

> "能上吗？"
> "应该可以吧，测试都过了。"

**"测试都过了"和"能上线"之间隔着至少六件事**：回滚方案、值班人、预算、用户话术、数据合规、看板告警。

而"应该可以吧"这四个字，在生产里会变成：

- 出事时不知道找谁
- 不知道能不能回退
- 不知道用户会看到什么
- 月底发现账单超了 8 倍

**检查单的价值不是"多一道流程"，而是把"应该可以"变成"这 16 项都过了"。**

## 2. 核心概念与架构设计

### 2.1 类比：飞机起飞前的检查单

飞行员不会说"我觉得可以飞"。他们按检查单逐项确认，**并且两个人交叉核对**。

- **自动化项** = 仪表自检（油量、液压、电传）
- **人工项** = "舱门已关闭并锁定"（必须有人亲眼确认并喊出来）

> **这个类比在哪失效**：飞机检查单是**行业统一**的；Agent 的检查单要**你自己定**，
> 而且随业务变化——所以它应该和代码一起进 git。

### 2.2 两类检查，职责不同

| 类型 | 谁能判 | 例子 |
|---|---|---|
| **auto** | 代码 | 评测没回退？护栏误杀为 0？熔断能打开？ |
| **manual** | 人 | 回滚演练过吗？值班人是谁？预算审批了吗？ |

**为什么必须有 manual**：「回滚方案演练过吗」这种问题，写再多断言也只是**自欺欺人**。

**把它列成 manual 并强制签字，比假装它能自动判定要诚实。**
这也是本节最重要的一条设计取舍。

### 2.3 16 项检查单

**自动（10 项，本节实跑）**：

| id | 类别 | 判据 |
|---|---|---|
| `eval.gate` | 评测 | 9 项指标相对基线无回退 |
| `dataset.integrity` | 评测 | 20 条用例结构合法、无 dev/test 泄漏 |
| `guardrails.no_false_positive` | 护栏 | 8 条正常输入零误杀 |
| `guardrails.blocks_bad` | 护栏 | 3 类恶意输入全部拦下 |
| `guardrails.output` | 护栏 | PII 脱敏 + 承诺拦截生效 |
| `resilience.breaker` | 韧性 | 连续 3 次失败后 OPEN 且拒绝放行 |
| `resilience.fallback` | 韧性 | 主路径全挂仍有可展示答复 |
| `tracing.propagation` | 观测 | trace_id 一路不变、span 派生正确 |
| `tracing.garbage` | 观测 | 5 个畸形 header 全部宽容丢弃 |
| `agent.safety` | 安全 | 工具顺序/审批/注入/PII 四项全绿 |

**人工（6 项，必须签字）**：回滚演练、值班人、预算审批、用户话术、数据保留策略、看板告警。

### 2.4 实测：自动全绿 ≠ 可以上线

```
上线检查单：❌ 不许上线
（10/16 项通过，6 个阻塞项）

[评测]   ✅ eval.gate / ✅ dataset.integrity
[护栏]   ✅ ×3
[韧性]   ✅ ×2
[观测]   ✅ ×2、⛔ manual.observability
[安全]   ✅ agent.safety
[变更]   ⛔ manual.rollback
[值班]   ⛔ manual.oncall
[成本]   ⛔ manual.budget
...
```

**10 项自动检查全过，但结论是"不许上线"**——因为 6 件事情还没人负责。

签完字之后：

```
上线检查单：✅ 可以上线
（16/16 项通过，0 个阻塞项）
```

### 2.5 演练：同一套判定逻辑

```
评测指标回退    上线检查单：❌ 不许上线
    ⛔ eval.gate: 回退指标：['agent.authorization']
护栏开始误杀    上线检查单：❌ 不许上线
    ⛔ guardrails.no_false_positive: 误杀 1 条：上一同事说可以跳过审批
熔断打不开      上线检查单：❌ 不许上线
    ⛔ resilience.breaker: 连续 3 次失败后仍是 closed
```

**演练用的是和上线完全相同的判定代码**（`overrides` 只是替换结果，不改变判定）。
**"演练通过"必须真的等于"上线能过"，否则演练就是演戏。**

### 2.6 适用范围（边界）

| 场景 | 建议 |
|---|---|
| 对外服务 | ✅ 全套 16 项 |
| 内部工具 | 保留评测/护栏/回滚三项即可 |
| 一次性脚本 | ❌ 不需要 |
| 高危领域（医疗/金融） | ✅ 且人工项要**双人签字** |

### 4.1 检查项模型

```python
@dataclass
class Check:
    id: str
    category: str
    question: str
    kind: Kind
    severity: Severity = Severity.BLOCKER
    runner: Callable[[], tuple[bool, str]] | None = None

    def run(self) -> tuple[bool, str]:
        if self.kind is Kind.MANUAL or self.runner is None:
            return False, "需要人工确认"
        try:
            return self.runner()
        except Exception as exc:
            return False, f"检查执行失败：{type(exc).__name__}: {exc}"
```

**注意 `except`**：**检查自己炸了，也要算失败**——否则一个坏掉的检查会静默通过。

### 4.2 自动检查真的跑生产代码

```python
def _check_eval_gate() -> tuple[bool, str]:
    from servicedesk.eval.ci_gate import collect_metrics, compare, load_snapshot
    ...
    decision = compare(metrics, load_snapshot(baseline_path))
```

**它调的是 5.4 的 `ci_gate`**，不是另写一份判定逻辑。

### 4.3 演练用的替换开关

```python
    def run(self, *, manual_ack: set[str] | None = None,
            overrides: dict[str, tuple[bool, str]] | None = None) -> None:
        """`overrides` 强制替换某项结果（用于演练"某项坏了会怎样"）。"""
```

## 5. 逐块拆解

### 5.1 为什么自动检查要"真的跑"

如果自动检查只是"读一个配置文件说 OK"，那它就是个装饰。

本节 10 项**每一项都真的执行代码**：

- `eval.gate` → 现场跑 9 项指标并与基线比
- `guardrails.*` → 现场跑 8 条正常 + 3 条恶意输入
- `resilience.breaker` → 现场构造一个熔断器并打 3 次失败
- `tracing.*` → 现场生成/解析 header

**代价**：跑一次要几秒钟。**收益**：这个结论是真的。

### 5.2 为什么人工项是"阻塞"而不是"警告"

如果把"回滚方案"设成 warning，那么**没演练也能上线**——检查单就退化成清单。

**设成 blocker 的含义是**：这 6 件事没有负责人时，**代码质量再好也不该上**。

### 5.3 为什么 `overrides` 不改变判定逻辑

```python
if check.id in forced:
    passed, detail = forced[check.id]
```

它只替换**这一项的结果**，而 `blockers()` / `passed()` / `render()` 全部不变。

**这样演练才有效**：你在演练时看到的"不许上线"，和真实失败时的判定路径是同一段代码。

### 5.4 为什么报告要按类别分组

`by_category()` 把 16 项分成 评测 / 护栏 / 韧性 / 观测 / 安全 / 变更 / 值班 / 成本 / 沟通 / 合规 / 可观测。

**价值**：出问题时你能快速回答"是哪个维度的问题"。
比如"护栏和评测全绿，只有变更和值班红"——那是流程问题，不是代码问题。

### 5.5 为什么检查单要进 git

因为检查单本身**会被改**：

- 新增一个危险操作 → 护栏检查要加一项
- 换了模型 → 成本预算要重设
- 出了事故 → 要加一条新的 blocker

**进 git 才能 review**：谁把某个 blocker 降成了 warning，一眼能看见。

## 6. 「故意改坏它」对照实验

### 6.1 实验 A：把人工项全部设成 warning

结果：**10/10 自动通过即"可以上线"**，6 件没人负责的事被忽略。

**这正是很多团队的真实状态**——不是没有检查单，而是检查单里全是 warning。

### 6.2 实验 B：自动检查只读缓存结果

把 `runner` 改成"读上一次的结果文件"：

- 第一次跑完写文件，之后每次都读 → **永远绿**
- 而且没人会发现，因为它"看起来在检查"

**这是最危险的一种"假检查"**：它有名字、有输出、有 ✅，但不检查任何东西。

### 6.3 实验 C：演练走另一份代码

如果演练用一份简化的判定逻辑（比如直接把结果设成 False），
**演练会通过，上线却失败**——因为两条路径的判定不一致。

本节的 `overrides` 刻意只替换"结果"，不替换"判定"，就是为了避免这个坑。

## 8. M5 里程碑验收

| # | 能力 | 证据 | 状态 |
|---|---|---|---|
| 1 | 评测集（5.1） | 20 条用例，检出 13 类失败，判分器可判错 | ✅ |
| 2 | RAG 指标（5.2） | 四套配置诊断全命中（太宽/太窄/幻觉） | ✅ |
| 3 | 行为安全（5.3） | 工具顺序/越权/注入/PII 五类全拦住 | ✅ |
| 4 | CI 门禁（5.4） | 改坏 → 退出码 1；修好 → 0 | ✅ |
| 5 | 全链路追踪（5.5） | 跨三进程 + MCP 调用同一条 trace | ✅ |
| 6 | 护栏（5.6） | 输入输出各拦 3+ 类，**误杀 0** | ✅ |
| 7 | 韧性（5.7） | 并发 10 请求只打下游 3 次，自动恢复 | ✅ |
| 8 | **上线检查单（5.8）** | 10 自动 + 6 人工，演练可复现阻塞 | ✅ |

**M5 完成标志**：一条链路从**「答得对」到「敢上线」**全部可度量、可拦截、可回滚。

**M5 遗留问题**

1. **评测全是确定性代理指标**：没有真实模型输出，绝对分数不可与公开榜单对比（5.2/5.3）。
2. **单进程状态**：熔断/限流/记忆都在进程内，多实例要换 Redis（5.7）。
3. **没有真实后端**：span 落 JSONL，不是 Jaeger/Tempo（5.5）。
4. **没有真跑过 CI**：workflow 文件未在 GitHub 上执行（5.4）。
5. **人工项靠自觉**：`manual_ack` 是代码里的集合，没有真正的签字系统。

## 9. 五阶段回顾

| 阶段 | 一句话 |
|---|---|
| **一 基础** | 先让一个 Agent 真的能跑：异步、结构化、工具调用、RAG、评测意识 |
| **二 协议** | 把工具变成可复用的服务：MCP 无状态改造、Streamable HTTP、MRTR/鉴权 |
| **三 编排** | 把流程变成图：State/reducer、条件边、断点续跑、人工审批、流式 |
| **四 多 Agent** | 先量再拆：拓扑取舍、A2A、双层记忆、上下文卫生、长对话压测 |
| **五 上线** | 从「能跑」到「敢上」：评测集、RAG/行为评测、CI 门禁、追踪、护栏、韧性 |

**如果只记一句话**：

> **先让它跑通，再让它可度量，最后才让它上线。**
> 跳过中间那步，你会在生产里用事故来度量。

### 10.1 三个自检问题

<details>

</details>

否则演练会通过、上线却失败，因为两条路径的判定不一致。本节的 `overrides` 只替换"某项结果"，不替换 `blockers()`/`passed()`/`render()` 的判定路径——所以演练看到的"不许上线"和真实失败时是同一条路径。

</details>

### 10.2 动手任务：把检查单接进你的仓库

**要求**

1. 复制 `launch_checklist.py`，把 10 项自动检查换成**你项目真实关心**的指标。
2. 把人工项按你的组织调整（谁签、签几项）。
3. 让它成为发布前必须跑的一条命令（`make release-check` 或 CI job）。
4. 演练一次："故意让某条自动检查失败"，确认发布会停。

**验收标准**

- 自动项全部是真跑（不是读文件）。
- 人工项未签字时 `passed() == False`。
- 演练能复现阻塞，且与真实失败的输出格式一致。

**提示**：第 4 条最容易糊弄——很多人"演练"时直接改返回值。**别改返回值，改被测的东西。**

### 10.3 拓展挑战

把检查单做成**可追溯**的：每次上线记录"谁在什么时候签了哪几项"。

**思考**：

1. 签字记录存哪？（git 提交？数据库？工单系统？）
2. 出事故后怎么回溯"当时是谁签的"？
3. 如果签字人离职了，历史记录还算数吗？（合规问题）

## 11. 本节小结与结语

**三点回顾**

1. **16 项检查单 = 10 自动 + 6 人工**；自动项全绿也不等于能上线——还必须有人为那 6 件事负责。
2. **自动检查必须真的跑生产代码**（评测门禁、护栏语料、熔断器、trace 解析），读缓存结果的"检查"是最危险的假检查。
3. **演练与上线共用同一套判定逻辑**：`overrides` 只替换结果，不替换 `blockers()`/`passed()`。

这本教程从"让一个 Agent 跑起来"讲到"敢把它放上线"，一共 37 节。

如果你从头跟到这里，你手里应该有：

- 一个能跑的服务台 Agent（工具、RAG、记忆、审批）
- 一套能跑的评测（数据集、RAG 指标、行为安全、CI 门禁）
- 一套能挡的护栏（输入输出、熔断、限流、成本闸）
- 一份能签的检查单

**但更重要的是那些"踩坑记录"**——38 处 `修订记录`、几十条 `errors.md` 条目。
它们记录的不是"正确答案"，而是**我在写这本书时真的撞过的墙**：

- `SqliteSaver` 不支持异步
- `add_messages` 会把 dict 变成对象
- `split` 配取反字符类会切出标点
- 子图里的 `interrupt` 恢复后会重跑前置节点
