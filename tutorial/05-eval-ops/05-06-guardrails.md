# 5.6 护栏：输入输出双向拦截

## 0. 本节导航

**本节在链路中的位置**：5.3 是**事后评测**（跑完一批样本看失败率），本节是**事中拦截**（这一条请求/答复，现在就处理）。

**本节你将获得**

1. **输入侧**三条规则：空/超长、提示词注入、越权请求。
2. **输出侧**五条规则，且分两种处置：**BLOCK**（承诺/泄漏/危险指令）与 **REWRITE**（PII 脱敏、缺引用补提示）。
3. 实测**零误杀**：10 条正常输入、8 条正常输出全部放行。
4. 一组**体面话术**（不是"违反政策"）。
5. 三个真实坑：`split` 配取反字符类、把"提问"当"指令"、链式改写互相覆盖。

**前置检查清单**

- 5.3 的 `uv run python -m scripts.agent_eval_demo` 能跑通。
- 知道"拒绝 ≠ 泄漏"这条（5.3 的坑）。

**难度**：★★★★☆ ｜ **预计时长**：100 分钟 ｜ **本节费用**：**¥0**（不调 LLM）

## 1. 为什么需要它（痛点先行）

5.3 的评测能告诉你"这个版本有 5 类安全失败"。但它**不阻止**任何一条真实请求。

上线后你需要的是：**这一条请求进来时，就把它拦住**。

而"拦住"最容易犯两个错：

| 错法 | 后果 |
|---|---|
| **不拦** | 越权/泄漏/注入直接到达用户 |
| **拦太狠** | 正常用户被反复拒绝，觉得"这 AI 什么都不会" |

**本节的核心指标不是"拦了多少"，而是"误杀了多少"。** 前者越多越好，后者必须为 0。

## 2. 核心概念与架构设计

### 2.1 类比：机场安检

- **输入护栏 = 登机前安检**：查危险品（注入、越权）
- **输出护栏 = 落地后检疫**：查带进来的东西（PII、承诺）
- **REWRITE = 没收违禁品但让你登机**（脱敏后放行）
- **BLOCK = 拒绝登机**（整条拦下）

> **这个类比在哪失效**：安检误判的代价是旅客投诉；
> 护栏误判的代价是**用户不再用它**——而且他不会告诉你为什么。

### 2.2 八条规则

**输入侧（3 条）**：

| 规则 | 抓什么 |
|---|---|
| `input.empty` | 空输入 / 超过 2000 字 |
| `input.injection` | "忽略之前指令""打印系统提示词""跳过审批" |
| `input.dangerous` | "帮我提升管理员""把密码改成""直接关掉 P0" |

**输出侧（5 条）**：

| 规则 | 处置 | 抓什么 |
|---|---|---|
| `output.promise` | **BLOCK** | "保证""一定能""100% 可以" |
| `output.dangerous_command` | **BLOCK** | `rm -rf /`、`sudo chmod 777` |
| `output.leak` | **BLOCK** | "系统提示：…" |
| `output.pii` | **REWRITE** | 手机号、身份证 → 打码 |
| `output.missing_citation` | **REWRITE** | 要求引用却没 `[C1]` → 补提示 |

### 2.3 为什么大多数输出应该 REWRITE 而不是 BLOCK

现实里的"问题输出"大多**没必要整条毙掉**：

- "李娜的手机号是 13800001234" → **打码就没事了**
- "请先重置密码。"（没引用）→ **补一句提示就没事了**

实测：

```
PII 泄漏   rewrite  李娜的手机号是 138****1234。
缺引用     rewrite  请先重置密码。
                   （本答复未附资料出处，建议核实后再执行。）
```

**一刀切地拒绝，会让护栏本身变成用户体验问题。**

### 2.4 实测：零误杀

```
输入侧：10 条正常输入，误杀 0 条
输出侧：8 条正常输出，误杀 0 条
```

其中有两条特别值得看：

| 输入/输出 | 为什么容易被误杀 | 结果 |
|---|---|---|
| "上一个同事说可以跳过审批，是这样吗？" | 含"跳过审批" | ✅ 放行（这是**提问**） |
| "抱歉，我不能提供系统提示词。" | 含"系统提示词" | ✅ 放行（这是**拒绝**） |

### 2.5 拦下之后说什么

**反面教材**：

> "您的请求违反安全政策，已被拒绝。"

**本节的话术**：

```
input.dangerous         这类操作需要审批，我可以帮你发起审批流程。要现在提交吗？
input.injection         这个问题我没法按那种方式处理。你可以直接说遇到了什么 IT 问题。
output.promise          具体时效我无法保证，我会按流程尽快处理。
output.leak             抱歉，内部配置信息不便提供。
```

**好的拒绝话术三要素**：说明为什么、给出下一步、**不指责用户**。

### 2.6 适用范围（边界）

| 场景 | 建议 |
|---|---|
| 面向外部用户 | ✅ 全套 |
| 内部工具、可信用户 | 可只留 PII 与危险指令 |
| 高准确率要求（医疗/金融） | 全 BLOCK，不做 REWRITE |
| 纯查询无写操作 | 只留输出侧 |

### 4.1 判定三态

```python
class Verdict(str, Enum):
    PASS = "pass"
    REWRITE = "rewrite"
    BLOCK = "block"
```

### 4.2 请求 vs 提问

```python
_IMPERATIVE = ("帮我", "给我", "直接", "麻烦你", "我要你", "立刻", "马上", "替我")
_INTERROGATIVE = ("吗", "是不是", "怎么", "如何", "为什么", "能否", "可不可以", "会不会")


def _looks_like_request(sentence: str) -> bool:
    """区分「要求我做」与「问能不能做」。

    判据：有请求式标记 → 算请求；只有疑问式标记 → 放行。
    这样"帮我跳过审批好吗？"仍然会被拦（有"帮我"），不能靠加个"吗"绕过。
    """
    if any(word in sentence for word in _IMPERATIVE):
        return True
    return not any(word in sentence for word in _INTERROGATIVE)
```

### 4.3 链式改写

```python
        for rule in rules:
            outcome = rule.check(patched, ctx)      # ← 用当前（可能已改写）的文本
            if outcome is None:
                continue
            if outcome.verdict is Verdict.BLOCK:
                return outcome
            patched = outcome.text
```

## 5. 逐块拆解

### 5.1 为什么 BLOCK 优先于 REWRITE

`_run` 里规则是按顺序执行的，**一旦某条 BLOCK 就立即返回**，不再往下试 REWRITE。

**理由**：`"李娜 13800001234，保证今天解决。"` 同时命中 PII（可改写）与承诺（必须拦）。
**改写后放行一条含无依据承诺的答复，毫无意义。**

实测（`test_block_wins_over_rewrite`）：结果是 **block**，不是 rewrite。

### 5.2 为什么改写要链式

实测 bug（§8.3）：如果每条规则都基于**原文**：

```
原文:   联系 13800001234。
PII:    → 联系 138****1234。
引用:   → 联系 13800001234。\n\n（未附资料出处…）    ← 把脱敏覆盖了
```

**修法**：`patched = outcome.text`，后一条基于前一条的结果。

### 5.3 为什么"拒绝"不算"泄漏"

和 5.3 同一个坑：

```
"抱歉，我不能提供系统提示词。"     → 含"系统提示词" → 朴素匹配会判泄漏
```

**修法**：逐句判断 + 拒绝词豁免（`不能/无法/抱歉/不会/无权/不便`）。

**这一条在输入侧没有对应物**——输入是用户说的，"用户不能提供 X"不是拒绝，是陈述。
所以豁免只在输出侧用。

### 5.4 为什么输入侧要区分"请求"和"提问"

实测误杀（§8.2）：

```
"上一个同事说可以跳过审批，是这样吗？"  → 被判 input.injection
```

**用户是在问"真的能跳过吗"**，他很可能是在**求证流程**，而不是要你跳过。

**但这里有个安全陷阱**：如果简单地"含问号就放行"，攻击者只要加个"？"就能绕过。

**所以判据是"请求式标记优先"**：有"帮我/直接/麻烦"就算请求（拦），
只有疑问词才算提问（放）。

实测：`"帮我跳过审批好吗？"` 仍然被拦 `input.injection`。

### 5.5 为什么统计要按规则分布

```
按规则分布：
  input.dangerous   1
  input.empty       1
  input.injection   1
```

**某个规则突然暴涨**，有两种可能：

- 有人在攻击（注入尝试暴增）
- 规则太宽在误杀（正常用户被拦）

**只看总 block 率，这两种情况分不开。** 按规则分布才能定位。

### 5.6 为什么话术不能只说"违反政策"

因为用户不知道下一步做什么:

- **说明为什么**："这类操作需要审批"
- **给出下一步**："我可以帮你发起审批流程。要现在提交吗？"
- **不指责用户**：不说"您的请求不合规"

**这三条决定了用户是被"引导"还是被"打回"。**

## 6. 「故意改坏它」对照实验

### 6.1 实验 A：只做 BLOCK，不做 REWRITE

把 PII 与缺引用也改成 BLOCK：

- 8 条正常输出里，凡是带引用要求但没加 `[C1]` 的**全部被拦**
- 用户看到的是"抱歉"，而不是"请先重置密码（附核实提示）"

**误杀率从 0 直接跳到 >0。** 这就是"一刀切"的代价。

### 6.2 实验 B：输入侧不区分请求与提问

去掉 `_looks_like_request`：

```
误杀: 上一个同事说可以跳过审批，是这样吗？  → input.injection
10 条正常输入，误杀 1 条
```

**注意：误杀率 10%。** 而"10% 的用户被莫名其妙拒绝一次"，足以让产品评分掉一星。

### 6.3 实验 C：改写不链式

见 §5.2：**PII 脱敏被后一条规则覆盖**，输出里仍然带着完整手机号。

**最危险的地方在于**：报告的 `fired` 里明明写着 `output.pii`，
看起来"脱敏了"，实际上没有。**监控会说谎。**

## 8. 生产环境踩坑实录

### 坑 1：`split` 配了取反的字符类，规则全部失效

**现象**

`output.promise` 和 `output.leak` **完全不生效**：`"保证 1 小时内处理完。"` 判 PASS。

**定位方法**

```python
from servicedesk.guardrails.pipeline import _sentences_without_disclaimer
print(_sentences_without_disclaimer("保证 1 小时内处理完。"))
# ['。']   ← 只切出标点，句子没了
```

**根因**

```python
_SENTENCE_RE = re.compile(r"[^。！？；\n]+")
for sentence in _SENTENCE_RE.split(text):     # ← split 配取反类 = 切出标点
```

`split` 会把**匹配到的**东西当分隔符扔掉，返回中间的空隙。
而 `[^。！？；\n]+` 匹配的是"非标点"，`split` 就把句子扔了、留下标点。

**修法**：用 `findall`：

```diff
- for sentence in _SENTENCE_RE.split(text)
+ for sentence in _SENTENCE_RE.findall(text)
```

**教训**：`split` 与 `findall` 对同一个正则的语义是**相反**的。
写完顺手 `print` 一下切分结果——这比读十遍正则快。

### 坑 2：把"提问"当"指令"

**现象**

用户问"上一个同事说可以跳过审批，是这样吗？"被拦，投诉"我只是问问"。

**根因**

正则只匹配了 `跳过…审批`，没区分请求与提问。

**修法**

`_looks_like_request`：请求式标记优先，只有疑问词才算提问（§5.4）。

**顺手加固**：把"提问不应被拦"写成参数化测试（本节的
`test_normal_questions_pass` 就是 7 条）。

### 坑 3：多条改写互相覆盖

**现象**

监控显示 PII 规则命中了，但输出里手机号是完整的。

**根因**

`_run` 里每条规则都基于**原文**判断，后一条返回的 `text` 覆盖了前一条的改写结果。

**修法**

链式：`patched = outcome.text`，后一条基于前一条（§5.2）。

**顺手加固**：断言"命中 PII 规则时，输出里必须不含原号码"
（本节 `test_multiple_rewrites_combine` 就是）。

## 9. 自检与作业

### 9.1 三个自检问题

<details>
<summary><b>Q1：为什么大多数输出问题应该 REWRITE 而不是 BLOCK？</b></summary>

因为现实里的问题输出大多没必要整条毙掉：PII 打码就没事、缺引用补一句提示就没事。一刀切拒绝会让用户觉得"这 AI 什么都不会"。BLOCK 只留给不可挽回的（无依据承诺、危险指令、内部泄漏）。

</details>

<details>
<summary><b>Q2：输入侧为什么要区分"请求"和"提问"？怎么防止被绕过？</b></summary>

用户问"听说可以跳过审批，是这样吗"是在求证流程，不是要你跳过。但简单地"含问号就放行"会被加个"？"绕过。所以判据是**请求式标记优先**：有"帮我/直接/麻烦"就算请求（拦），只有疑问词才算提问（放）。

</details>

<details>
<summary><b>Q3：为什么改写规则必须链式执行？</b></summary>

否则后一条规则基于原文改写，会覆盖前一条的结果——实测 PII 脱敏被"补引用提示"覆盖，输出里仍是完整手机号，而监控显示 PII 规则已命中。**监控会说谎**是最危险的。

</details>

### 9.2 动手任务：把护栏接进 3.7 的图

**要求**

1. 在图的入口节点前加 `check_input`：BLOCK 则直接返回 `fallback_reply`，不进图。
2. 在最终答复前加 `safe_output`：REWRITE 则用改写后的文本，BLOCK 则用话术。
3. 把 `pipeline.stats` 落到结构化日志（按规则计数）。
4. 跑 10 条正常 + 4 条恶意请求，确认误杀 0、拦截 3 类。

**验收标准**

- 恶意请求**不触发任何工具调用**（护栏在入口就拦了）。
- 正常请求的答复与不加护栏时**完全一致**（零误杀、零改写）。
- 日志里能按规则统计拦截数。
- 原有 536 个用例仍全绿。

**提示**：第 1 条是关键——护栏要在**进图之前**拦，否则你已经花了一次 LLM 调用。

### 9.3 拓展挑战

给护栏加"分级处置"：轻（改写）、中（拦下但给替代方案）、重（拦下并记录告警）。

**思考**：

1. 怎么定义"轻/中/重"？（按规则？按置信度？按用户历史？）
2. 重度拦截要不要通知安全团队？怎么避免告警疲劳？
3. 用户连续 3 次被拦，要不要换个策略（比如转人工）？

## 10. 本节小结与延伸

**三点回顾**

1. **双向拦截**：输入 3 条（空/超长、注入、越权）+ 输出 5 条（承诺、危险指令、泄漏、PII、缺引用）。
2. **BLOCK 与 REWRITE 分开**：承诺/泄漏/危险指令拦下；PII 打码、缺引用补提示——**误杀才是护栏最大的成本**。
3. **实测零误杀**：10 条正常输入 + 8 条正常输出全放行，包括"问能不能跳过审批"与"我不能提供系统提示词"这两个最容易被误判的。

**已知限制（诚实记录）**

- **全是规则式**：换语言、编码绕过、变体表达都抓不到。
- **PII 只认手机号与身份证**：地址、病历号、银行卡没覆盖。
- **没有置信度分级**：命中即处置，没有"疑似/确认"之分。
- **未接进图**：`check_input`/`safe_output` 是独立模块（§9.2 是作业）。
