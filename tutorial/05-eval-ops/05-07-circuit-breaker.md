# 5.7 熔断、降级、限流与成本闸

## 0. 本节导航

**本节在链路中的位置**：5.6 挡的是"坏请求"，本节挡的是**"太多请求"和"太贵的请求"**，以及"下游已经坏了还要不要打"。

**本节你将获得**

1. **令牌桶限流**（按 key 分桶）——以及为什么不用固定窗口。
2. **熔断三态机**：连续失败 → OPEN（**不再发起调用**）→ 冷却 → HALF_OPEN 探测 → 成功回 CLOSED。

## 1. 为什么需要它（痛点先行）

上线之后，让 Agent 挂掉的原因通常不是"答错了"，而是这三件：

| 事故 | 症状 |
|---|---|
| **下游挂了还死打** | 模型接口超时，你的服务把线程/连接全占满，**级联雪崩** |
| **被刷爆** | 一个用户/爬虫把额度用完，所有人一起 429 |
| **账单爆炸** | 月底发现花了 8 倍预算，因为没人拦"贵请求" |

**这三件事有一个共同点：它们都不是"功能 bug"，而是"没有闸门"。**

## 2. 核心概念与架构设计

### 2.1 类比：高速公路的四道设施

- **限流 = 匝道红绿灯**：车流太密就分批放行
- **成本闸 = 收费站的余额检查**：没钱了不让上
- **熔断 = 前方事故封路**：已经有事故了，别再放车进去
- **降级 = 绕行路线**：封路了，但你能走另一条（慢一点而已）

> **这个类比在哪失效**：封路是**人**决定的；熔断是**自动**的，
> 而且它会在冷却后**自己试探**（HALF_OPEN）——没人通知它"路修好了"。

### 2.2 四道闸的顺序（**最重要的一节**）

```
① 限流（内存判断，最便宜）
   ↓ 通过
② 成本闸（一次加法，次便宜）
   ↓ 通过
③ 熔断（看下游历史）
   ↓ 允许
④ 调主路径（最贵：网络 + LLM + 钱）
   ↓ 失败
⑤ 降级链（缓存 → 模板 → 兜底话术）
```

**为什么顺序不能反**：把贵的判断放前面，等于**你已经花了钱才发现该拦**。

> 本节实测时，一个测试恰好暴露了这件事（§8.1）：限流器容量设成 2，
> 第三次调用被**限流**拦下，而不是熔断——因为限流在熔断前面。

### 2.3 熔断三态机

```
        CLOSED ──(连续失败 >= threshold)──► OPEN
          ▲                                   │
          │                             (冷却时间到)
          └──(探测成功)── HALF_OPEN ◄─────────┘
                            │
                       (探测失败) → 回 OPEN 并重新计时
```

**三个容易搞错的点**：

1. **OPEN 期间不发起调用**——不是"调了再判断失败"
2. **HALF_OPEN 只放少量探测**（本节默认 1 个），否则等于没熔断
3. **探测失败要重新计时**，不是"再失败一次就关"

### 2.4 令牌桶 vs 固定窗口

| | 固定窗口 | 令牌桶 |
|---|---|---|
| 实现 | 每分钟计数清零 | 容量 + 匀速补充 |
| 边界问题 | **59.9s 放 100 + 60.1s 放 100 = 2 秒 200** | 平滑，无翻倍 |
| 突发容忍 | 无 | 有（桶里攒着） |

### 2.5 实测：并发 10 个请求

```
并发 10 个请求（容量 5，失败阈值 3）：
  降级分布: {'cache': 10}
  下游实际被调用: 3 次
  熔断状态: open
  限流拒绝: {'u-1': 5}
```

**读法**：

- 10 个请求里，5 个被限流（容量 5）
- 另外 5 个进了熔断判断，前 3 个打到下游（然后失败）
- 后 2 个被熔断拒绝（OPEN）
- **10 个请求全部拿到了答复**（降级到缓存）

**"下游只被打了 3 次"是本节最关键的数字**——这就是熔断的全部价值。

### 2.6 适用范围（边界）

| 场景 | 建议 |
|---|---|
| 调外部模型/API | ✅ 全套 |
| 内部纯计算 | 只留限流 |
| 单用户工具 | ❌ 不需要 |
| 多租户 SaaS | ✅ 且要按租户分桶 + 分账 |

### 4.1 熔断器

```python
    def _refresh(self) -> None:
        """按冷却时间推进状态：OPEN 到点了就进 HALF_OPEN。"""
        if self.state is BreakerState.OPEN and self.clock() - self.opened_at >= self.cooldown_s:
            self.state = BreakerState.HALF_OPEN
            self.half_open_inflight = 0
            self.failures = 0

    def allow(self) -> bool:
        self._refresh()
        if self.state is BreakerState.CLOSED:
            return True
        if self.state is BreakerState.OPEN:
            self.rejected += 1
            return False
        if self.half_open_inflight < self.half_open_max_calls:
            self.half_open_inflight += 1
            return True
        self.rejected += 1
        return False
```

### 4.2 令牌桶

```python
    def _refill(self) -> None:
        now = self.clock()
        elapsed = max(0.0, now - self.last_refill)
        self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_per_s)
        self.last_refill = now

    def try_take(self, amount: float = 1.0) -> bool:
        self._refill()
        if self.tokens >= amount:
            self.tokens -= amount
            return True
        return False
```

## 5. 逐块拆解

### 5.1 为什么时钟要可注入

```python
@dataclass
class FakeClock:
    t: float = 1000.0
    def __call__(self) -> float: return self.t
    def advance(self, seconds: float) -> None: self.t += seconds
```

熔断和限流都要"等时间"：冷却 5 秒、每秒补 1 个令牌。
**如果测试里真等 5 秒**：十几个用例就是一分多钟，而且不稳定。

**可注入时钟让"等 5 秒"变成 `clock.advance(5)`——瞬间、确定。**

### 5.2 为什么 `_refresh` 在 `allow` 和 `as_dict` 里都调用

因为它**只根据时间推导状态**，是幂等的：调几次结果一样。

这带来一个好处：**你不必有一个后台线程定时检查"冷却到了没"**——
谁问就谁算。少一个线程，少一类 bug。

### 5.3 为什么 HALF_OPEN 要限制探测数

如果冷却后**放所有请求进去**，那就等于"每 5 秒全量打一次下游"——
下游刚恢复又被你打挂，形成**周期性雪崩**。

本节默认 `half_open_max_calls=1`：**一次只放一个，成了就全放，不成继续等。**

### 5.4 为什么成本闸按"天"重置

因为预算是**按月/按天**批的。实测：

```
每日预算 1000 token。每次调用估 300。
  第 1 次: ✅ 放行   剩余 700
  第 2 次: ✅ 放行   剩余 400
  第 3 次: ✅ 放行   剩余 100
  第 4 次: ⛔ 拒绝   剩余 100
  第 5 次: ⛔ 拒绝   剩余 100
```

注意第 4、5 次：**剩余 100 但估 300，所以拒绝**。不是"花超了才拦"，
而是"**预估要花的钱不够就拦**"。

### 5.5 为什么降级链要按"像原答案"排序

```
一切正常              primary     模型生成的答复
模型挂了，缓存命中    cache       上一次的缓存答复
模型挂了，缓存也没    template    通用排查步骤：请先重启客户端、检查网络。
```

**缓存排第一**，因为它是"这个用户/这个问题的真实答案"，只是旧了点。
**模板排第二**，因为它至少还是个答案。
**兜底话术排最后**（"服务暂时不可用"）——它几乎没信息量，但比报错好。

### 5.6 为什么降级也要"记账"

```python
    def _count(self, tier: str) -> None:
        self.tier_counts[tier] = self.tier_counts.get(tier, 0) + 1
```

`tier_counts` 能回答一个关键问题：**"我们的降级率是多少？"**

如果 `cache` 占了 40%，说明主路径经常不可用——**这不是"韧性好"，是"主路径有故障"**。
**降级率和熔断率必须进监控**，否则你会把"一直在降级"误认为"一直很稳"。

## 6. 「故意改坏它」对照实验

### 6.1 实验 A：去掉熔断，只做重试

下游挂了 → 每个请求都重试 3 次 → 10 个并发请求 = **30 次下游调用**（本节是 3 次）。

**这就是级联雪崩的机制**：你的"重试"把下游彻底打死了。

### 6.2 实验 B：HALF_OPEN 不限制探测数

冷却时间一到，**所有排队的请求一起放行** → 下游刚恢复又被冲垮 →
立刻重新 OPEN → 5 秒后再来一波。**周期性雪崩**，比一直 OPEN 还糟。

### 6.3 实验 C：成本闸放在熔断后面

顺序变成"熔断 → 成本"：

- 熔断 OPEN 时，你**根本走不到成本闸**
- 但账单不是这么算的——**熔断期间你确实没花钱，可一旦恢复，成本闸才发现早就超了**

**顺序的意义**：成本闸要在**任何花钱动作之前**，而不是"在熔断之后"。

## 8. 生产环境踩坑实录

### 坑 1：以为在测熔断，其实被限流拦了

**现象**

写了个测试："连续失败 3 次后熔断"。跑出来 `reason` 是
`rate_limited: 请求过于频繁`，不是 `circuit_open`。

**定位方法**

看 `reason` 而不是只看 `tier`——两者都降级到了 `cache`，但原因完全不同。

```
CallResult(ok=False, text='缓存答复', tier='cache',
           reason='rate_limited: 请求过于频繁')     ← 不是熔断
```

**根因**

测试夹具里限流容量设成了 2，第三次请求还没走到熔断就被限流拦了。

**修法**

夹具里把限流容量放大（10），单独再用一个小容量的测试覆盖限流。

**这条坑的价值**：它**实证了顺序是真实的**——限流真的在熔断前面。

### 坑 2：熔断期间还在重试

**现象**

下游故障期间，QPS 不降反升。

**根因**

外层重试逻辑不知道熔断器已经 OPEN，还在"失败 → 重试 → 再失败 → 再重试"。

**修法**

**重试必须在熔断器之内**：先问 `breaker.allow()`，允许了才重试。
本节的 `ResilienceManager.call` 就是"一次调用"，重试策略应包在它外面，
且重试前也要过 `allow()`。

**顺手加固**：把"熔断拒绝次数"和"重试次数"分开监控——
前者涨说明下游坏，后者涨说明你的重试策略有问题。

### 坑 3：降级率 40% 却没人发现

**现象**

用户反馈"答案总是很模板化"，一查发现 40% 的请求走了降级。

**根因**

降级不报错、不影响可用性，**监控只看错误率，看不到降级率**。

**修法**

`tier_counts` 进监控，并设阈值告警（比如降级率 > 10% 就告警）。

**顺手加固**：把"降级原因"也打点（rate_limited / cost_limited / circuit_open / error）——
**同样的 40%，原因不同，处置完全不同。**

## 9. 自检与作业

### 9.1 三个自检问题

<details>
<summary><b>Q1：熔断和重试是什么关系？</b></summary>

**互斥**。重试是"再试一次可能就好了"；熔断是"已经确定坏了，别再试"。熔断 OPEN 时**不发起任何调用**，所以外层重试必须先问 `breaker.allow()`，否则"重试"会把下游彻底打死（实测 10 个并发 × 3 次重试 = 30 次调用 vs 熔断的 3 次）。

</details>

<details>
<summary><b>Q2：为什么四道闸的顺序是"限流 → 成本 → 熔断 → 调用"？</b></summary>

因为便宜的要放前面。限流是一次内存判断，成本闸是一次加法，熔断要看下游历史，调用要花网络和钱。把贵的放前面等于"已经花了钱才发现该拦"。本节实测时一个测试恰好暴露了这件事：限流容量小的时候，请求根本没走到熔断。

</details>

<details>
<summary><b>Q3：降级到缓存和"直接报错"有什么区别？</b></summary>

缓存是"这个用户的真实答案，只是旧了点"；报错是"什么都没有"。降级的目标不是"正确"，而是"**还有用**"。但降级率必须监控——40% 的降级说明主路径有故障，不是"韧性好"。

</details>

## 10. 本节小结与延伸

**三点回顾**

1. **熔断不是重试**：OPEN 期间**不发起调用**（实测 6 个请求只打了 3 次下游），HALF_OPEN 只放 1 个探测，失败要重新计时。
2. **四道闸顺序**：限流 → 成本 → 熔断 → 调用；**便宜的在前**，否则白花钱。
3. **降级不是返回错误**：缓存 → 模板 → 兜底话术；但**降级率必须进监控**，40% 的降级是故障不是韧性。

**已知限制（诚实记录）**

- **单进程状态**：多实例部署时每个实例各有一份熔断/限流状态（生产要用 Redis）。
- **成本是估算**：用 `estimated_tokens`，不是真实 tokenizer。
- **没有抖动（jitter）**：多个实例可能同时进入 HALF_OPEN。
- **没有自适应**：令牌速率、熔断阈值都是静态配置（§9.3）。
- **未接入主链路**：`ResilienceManager` 还没包住 2.7 的工具调用（§9.2 是作业）。
