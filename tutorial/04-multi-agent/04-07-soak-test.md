## 1. 为什么需要它（痛点先行）

前面三节的验证都是"单点正确"：

- 4.4：一段会话压完，约束还在
- 4.5：一条记忆能召回
- 4.6：一次污染被拦

**但真实系统不是跑一次，是跑一万次、每条会话几十轮。** 单点正确不等于长期可用：

- 压到第 40 轮时，第 5 轮说的工单号还在吗？
- 每轮都发一次完整上下文，50 轮下来一共付了多少？
- 污染混进来 3 次，拦住了几次？

**这些只有压测能回答。**

## 2. 核心概念与架构设计

### 2.1 类比：油耗测试

- **单点正确** = 发动机台架测试（某个转速下正常）
- **压测** = 满载跑 500 公里，量**总油耗**和**故障数**

> **这个类比在哪失效**：车的油耗只看总油量；
> 而 LLM 的成本是**每一轮都要重发整个上下文**——所以要看"每轮大小之和"，
> 不是"最后剩多少"。

### 2.2 成本该怎么量（**本节最重要的概念**）

假设每轮上下文是 `t_i` 个 token，跑 `N` 轮：

```
真实成本 ≈ Σ t_i         （不是 t_N）
```

**为什么**：每次调模型，你都要把**当前整个上下文**发过去。
所以第 1 轮的 100 token 被发了 50 次，第 50 轮的 2700 token 只发了 1 次——
**早期的 token 更贵**（被重复发送的次数更多）。

**这条直接推出一个结论**：**压得越早，省得越多。**
等到"快爆了"才压，前面几十轮的膨胀已经付过钱了。

### 2.3 四种配置

| 配置 | 预算 | 策略 | 卫生 |
|---|---|---|---|
| **baseline** | 无 | 不压缩 | 否 |
| **window** | 400 | window | 否 |
| **hybrid** | 400 | hybrid + pin | 否 |
| **full** | 400 | hybrid + pin | 是 |

### 2.4 实测结果（50 轮）

| 配置 | 最终 token | 峰值 | **累计成本** | 压缩次数 | 约束保留 | 污染拦截 |
|---|---|---|---|---|---|---|
| baseline | 2733 | 2733 | **68,095** | 0 | 4/4 | 0/3 |
| window | 146 | 397 | 11,154 | 8 | **0/4** | 0/3 |
| hybrid | 375 | 400 | 13,513 | 10 | **4/4** | 0/3 |
| full | 375 | 400 | 13,513 | 10 | **4/4** | **2/3** |

**三句话读完这张表**：

1. **baseline 不丢任何东西，但贵 5.0 倍**（68,095 vs 13,513）
2. **window 最便宜（11,154），但 4 条约束全丢**
3. **hybrid 只比 window 贵 21%，把 4 条约束全保住了**

### 2.5 成本曲线（每 10 轮采样）

| 轮次 | baseline | window | hybrid | full |
|---|---|---|---|---|
| 10 | 540 | 204 | 292 | 292 |
| 20 | 1091 | 146 | 354 | 354 |
| 30 | 1640 | 319 | 254 | 254 |
| 40 | 2186 | 178 | 279 | 279 |
| 50 | 2733 | 146 | 375 | 375 |

**baseline 一路爬升**（每 10 轮插一次大块工具返回就跳一截），
其余三条被预算压住，在 400 附近震荡。

### 2.6 适用范围（边界）

| 场景 | 建议 |
|---|---|
| 会话 < 10 轮 | 别压，压了反而丢信息 |
| 10–50 轮 | hybrid + 预算 |
| 50–500 轮 | hybrid + 长期记忆（4.5）分担 |
| > 500 轮 | 该做"会话归档 + 分层摘要"了，本节不覆盖 |

### 4.1 压测夹具

```python
# 在第几轮注入约束（模拟"用户中途强调重要事项"）
CONSTRAINT_ROUNDS: dict[int, str] = {
    5: "我的工单号是 T-1001，后面都用它称呼。",
    12: "注意：不要重置我的密码，我有重要会议。",
    25: "这条工单必须在今天下班前处理完。",
    38: "审批已通过，可以直接执行。",
    47: "最后确认一次：工单号还是 T-1001。",
}
```

**注意第 47 轮**：它重复了 T-1001。抽取时会**去重**，所以 5 条消息 → 4 个约束。
这是个真实特性（用户重复强调同一件事），测试里也显式断言了这一点。

### 4.2 成本累加

```python
        current = history.tokens()
        result.curve[round_index] = current
        result.peak_tokens = max(result.peak_tokens, current)
        result.cumulative_tokens += current         # 每一轮都要发一次完整上下文
```

**这一行就是"真实成本"**：`+=` 而不是 `=`。

### 4.3 约束保留统计

```python
    all_text = " ".join(message.content for message in history.messages)
    injected = extract_constraints([_as_message(text) for text in CONSTRAINT_ROUNDS.values()])
    result.constraints_injected = [f"{item.kind}:{item.text}" for item in injected]
    result.constraints_retained = [
        f"{item.kind}:{item.text}" for item in injected if item.text in all_text
    ]
```

**判据是"短语还在不在最终上下文里"** —— 和 4.4 的 `lost_constraints` 同一套保守判据。

## 5. 逐块拆解

### 5.1 为什么 `baseline` 也保留 4/4

因为它根本没压缩——所有消息都在。

**这个对照组是必要的**：它证明"约束丢失"不是抽取逻辑的问题，
而是**压缩策略的选择**问题。没有这个对照，你分不清"丢了"是策略的锅还是代码的 bug。

### 5.2 为什么 `window` 是 0/4

`window` 只保留最近 4 条消息。

50 轮跑完，最近 4 条是第 50 轮的一问一答 + 前两条——第 5 轮、第 12 轮、第 25 轮、第 38 轮**全在被丢的区间里**。

**这就是"只留最近的"最真实的代价**：用户强调过 4 次的事，一次都不剩。

### 5.3 为什么 hybrid 贵 21% 却值得

```
window : 11,154
hybrid : 13,513   （+21%）
```

多出的 2,359 token 买了什么？**4 条约束全部留住**（T-1001、不要重置密码、今天处理完、已批准）。

对比一下"丢掉它们"的代价：

- 不知道工单号 → 反复问用户 → 多 1–2 轮对话（每轮几千 token）
- 不知道禁令 → 重置了密码 → 一次事故

**21% 的溢价，是这个压测里最划算的一笔交易。**

### 5.4 为什么污染拦截只有 2/3

三条污染分别是：

| 类型 | 处理 | 计入 blocked? |
|---|---|---|
| 跨用户（别人的手机号） | 命名空间丢弃 | ✅ |
| 低权威（网络偏方） | 来源权重丢弃 | ✅ |
| **过期知识库**（500 天前） | **只标注「可能过期」，不丢弃** | ❌ |

**第三条是刻意的**：有些旧信息不能删（老客户端仍需要旧安装包），
但必须让模型看见它旧。**丢弃是二选一，标注是把判断权交回去。**

### 5.5 为什么曲线不是单调的

`window` 的曲线：204 → 146 → 319 → 178 → 146。

因为压缩是"超了才压"：压完降到 146，下一轮涨到 319 又超了，再压回 178……

**这不是 bug，是"阈值触发"的正常表现。** 如果想让曲线平滑，改成"到 70% 就压"
（4.4 §5.4 的建议），代价是压缩更频繁。

### 5.6 这个压测的可复现性

- 固定时钟常量（`NOW`），不用 `time.time()`
- 固定模板文本，不用随机数
- 同样的输入跑两遍，结果 `as_dict()` 完全一致（`test_deterministic` 断言了）

**压测必须可复现**，否则"这次省了 80%"下次可能变成 70%，你无法判断是改动导致的还是噪声。

## 6. 「故意改坏它」对照实验

### 6.1 实验 A：把成本算成"最后一轮大小"

用 `final_tokens` 代替 `cumulative_tokens`：

| 配置 | final_tokens | 看起来谁最贵？ |
|---|---|---|
| baseline | 2733 | 最贵 ✅ |
| window | 146 | 最便宜 |
| hybrid | 375 | 中间 |

**结论碰巧一样**（baseline 最贵），但幅度完全错了：`2733 vs 375` 是 **7.3 倍**，
而真实成本是 `68095 vs 13513` = **5.0 倍**。

**更危险的情况**：如果某个策略"每轮都压到很小、但每轮都触发压缩"，
`final_tokens` 会很小，`cumulative_tokens` 却可能更大。**用错指标会选出错的方案。**

### 6.2 实验 B：去掉 pinning 跑 hybrid

4.4 已经实测过：忘了 `pin_all_constraints()` 的 hybrid 会退化成 window。
放到 50 轮压测里，就是**4/4 变成 0/4**。

**这个 bug 在短会话里看不出来**（10 轮内约束还在最近 4 条里），
**只有压测才会暴露**。

### 6.3 实验 C：把预算调大

把预算从 400 调到 4000：

- 压缩次数从 10 降到 0（因为一直没超）
- 结果变成 baseline（473 轮的总量），成本回到 68,095 附近

**预算不是"越大越好"**：预算大 = 少压缩 = 贵。而预算小 = 多压缩 = 可能丢信息。
**400 这个值是从"最近 4 条 + 几条 pinned"倒推的，不是拍脑袋。**

| 5 | 长期记忆与遗忘（4.5） | 90 天前工单排第 1，TTL 过期不被召回 | ✅ |

| 7 | **长对话压测（4.7）** | **50 轮后约束 4/4 仍在，成本省 80%** | ✅ |

**M4 完成标志**：一条长对话能分支、能协作、能记忆、不忘约束、不吸污染，并且**成本可控**。

**M4 遗留问题（带进阶段五）**

1. **没有真实 LLM**：压缩摘要、调度决策都是规则式的（阶段五会引入真实模型 + 评估集）。
2. **token 是估算**：不是真实 tokenizer，绝对值会偏。
3. **污染是注入的**：不是模型自己产生的幻觉。
4. **单用户、无并发**：多租户互相干扰没测。
5. **> 500 轮的场景没覆盖**：需要会话归档 + 分层摘要。

## 9. 生产环境踩坑实录

### 坑 1：用"最后一轮大小"当成本指标

**现象**

优化了一个压缩策略，`final_tokens` 从 800 降到 300，很开心。
上线后账单没降，反而涨了——因为新策略**每轮都触发压缩**，压缩本身有开销（摘要调用）。

**定位方法**

看"每轮上下文大小"的曲线，而不是最后那个点：

```python
for round_index, tokens in result.curve.items():
    log.info("context_size", round=round_index, tokens=tokens)
```

**修法**

成本指标改成 `Σ t_i`（本节 `cumulative_tokens`）。

**顺手加固**：把"压缩次数"和"压缩开销"一起看——**压缩不是免费的**。

### 坑 2：短会话测不出约束丢失

**现象**

本地用 8 轮会话测了一切正常，上线后用户投诉"Agent 忘了我说的禁忌"。

**原因**

8 轮会话里，第 1 轮的约束还在"最近 4 条"里，`window` 也能留住。
**只有跑长会话才会暴露。**

**修法**

把压测固定成 CI 的一部分（本节 50 轮跑完只要几秒，完全跑得起）。

**顺手加固**：压测的轮数应该覆盖"最短的会被投诉的会话长度"——本节的 50 是保守值。

### 坑 3：压测不可复现，数字对不上

**现象**

同样的代码，两次跑出来的成本差 15%，无法判断改动有没有效果。

**原因**

用了 `time.time()`、随机数、或依赖字典顺序。

**修法**

- 固定时钟常量
- 固定语料
- 断言"两次跑结果完全一致"（`test_deterministic`）

**顺手加固**：把压测结果的 `as_dict()` 存成基线文件，改动后对比——这就是最朴素的回归测试。

## 10. 自检与作业

### 10.1 三个自检问题

<details>
<summary><b>Q1：为什么成本要用「每轮上下文大小之和」，而不是最后一轮的大小？</b></summary>

因为每次调模型都要把**当前整个上下文**发过去。第 1 轮的 100 token 被发了 50 次，第 50 轮的 2700 token 只发 1 次——早期的 token 更贵。用最后一轮大小会严重低估，而且会选出"每轮都压得很小但每轮都压"的错误方案。

</details>

<details>
<summary><b>Q2：window 最便宜（11,154），为什么不能用它？</b></summary>

因为它把 4 条关键约束全丢了（0/4）。用户第 5 轮说的工单号、第 12 轮说的禁令，到第 50 轮一条都不剩。省下的 2,359 token（相对 hybrid）远不够赔一次"把客户密码重置了"的事故。

</details>

<details>
<summary><b>Q3：污染拦截为什么只有 2/3？</b></summary>

因为第三条是"过期知识库条目"，处理方式是**标注「可能过期」而不是丢弃**。有些旧信息不能删（老客户端仍需要旧安装包），丢弃会损失信息量。**丢弃是二选一，标注是把判断权交回去。**

</details>

### 10.2 动手任务：把压测接进 CI

**要求**

1. 把 `run_all(rounds=50)` 的结果存成 `baseline.json`（提交进仓库）。
2. 写一个对比脚本：新结果 vs baseline，任何指标劣化超过阈值就退出码非 0。
3. 阈值建议：累计成本 +10%、约束保留率 -5%、污染拦截 -1。
4. 在 CI 里跑它（几秒钟，完全跑得起）。

**验收标准**

- `baseline.json` 提交后，同样的代码跑出来**完全一致**（0 差异）。
- 故意把 `pin_all_constraints()` 删掉，CI 必须红（约束保留 4/4 → 0/4）。
- 故意把预算改成 4000，CI 必须红（成本 +400%）。

**提示**：第 2 条是这套机制的价值所在——**它把"压缩策略不能被悄悄改坏"变成了机器可检查的事**。

### 10.3 拓展挑战

加一个"1000 轮"的超长压测，并设计分层摘要：

1. 最近 N 轮：原样保留
2. 中期：每 10 轮压成 1 条摘要（滚动摘要）
3. 远期：只保留"结论"与"约束"

**思考**：

1. 滚动摘要的"摘要的摘要"会不会累积失真？怎么测？
2. 1000 轮下 `cumulative_tokens` 会是多少？还能不能算"可控"？
3. 什么信号说明"这次会话该归档了"？（轮数？tokens？还是"话题切换"？）

## 11. 本节小结与延伸

**三点回顾**

1. **成本 = 每轮上下文大小之和**，所以**压得越早省得越多**；用"最后一轮大小"会严重低估并选错方案。
2. **50 轮实测**：window 最便宜但丢光 4 条约束（0/4）；hybrid 只贵 21% 全保住（4/4）；baseline 贵 5 倍。
3. **丢弃与标注是两种不同手段**：污染拦截 2/3 而不是 3/3，是因为过期信息选择"标注"而非"丢弃"。

**已知限制（诚实记录）**

- **无真实 LLM**：摘要与调度是规则式。
- **token 是估算**（`estimate_tokens` 按字符折算），绝对值有偏差。
- **污染是注入的**，不是模型自己产生的幻觉。
- **单用户、无并发**。
- **只测到 50 轮**：1000 轮需要分层摘要（§10.3）。
