# 4.5 双层记忆（二）：长期语义 + 情景记忆与遗忘

## 0. 本节导航

**本节在链路中的位置**：4.4 解决"这一轮塞不下"，本节解决"**下次还认得你**"。两者合起来才是完整的双层记忆。

**本节你将获得**

1. **语义记忆**（用户偏好）与**情景记忆**（历史事件）的检索逻辑差异。
2. 一个打分公式：**0.6·相似度 + 0.25·重要性 + 0.15·新鲜度**。
3. **验收实测**：三个月前的工单在新会话里排第 1（相似度 0.362），
   而过期的验证码**没有被召回**。
4. 遗忘三件套：**TTL / 显式删除 / 用户级删除**（被遗忘权）。
5. 一个反直觉的对比：90 天前的工单（0.4157）与 3 天前的偏好（0.4143）**只差 0.0014**——
   权重稍有变化，冠军就换人。

- 1.x 的 `HashEmbedder`（`rag/embedder.py`）已了解。

## 1. 为什么需要它（痛点先行）

4.4 的短期记忆有个前提：**同一个会话**。会话一结束，全部作废。

但客服场景里最值钱的信息恰恰是跨会话的：

- "这个用户上个月为同一个 VPN 问题来过三次" → 该升级处理
- "他偏好邮件联系，别打电话" → 别踩雷
- "上次是重置密码解决的" → 直接给答案，别再走一遍排查

**没有长期记忆，每次都是陌生人。**

而长期记忆有个反直觉的难点：**不是"记不住"，而是"忘不掉"**。

一个从不遗忘的记忆库会变成什么样？

- 三年前的偏好还在（他早就换了部门）
- 一次性验证码还在（早过期了）
- 已解决的工单还在（同样的问题又来，召回一堆"已解决"的旧记录，淹没了真正的答案）

**所以本节一半的篇幅讲"遗忘"。**

## 2. 核心概念与架构设计

### 2.1 类比：病历 vs 日记

- **语义记忆 = 病历首页**：血型、过敏史、慢性病。**每次就诊都要看**，与今天看什么病无关。
- **情景记忆 = 就诊记录**：3 月 12 日因咳嗽就诊、开了什么药。**按今天症状去翻相关的**。

> **这个类比在哪失效**：病历首页是"当前有效"的（过敏史不会随时间衰减）；
> 而记忆库里的语义条目也会过期（"他喜欢电话联系"可能已经不成立了）。
> 所以语义记忆同样需要 TTL，只是可以给得长得多。

### 2.2 两类记忆的检索逻辑不同

| | 语义记忆 | 情景记忆 |
|---|---|---|
| 内容 | 偏好、身份、长期约束 | 某天发生了什么 |
| 该不该每次带上 | **是**（几乎恒置） | 否，按相关性 |
| 排序依据 | 重要性为主 | 相似度为主 |
| 生命周期 | 长（可数月/数年） | 中（可数周/数月） |

**所以"合并两类记忆"不是拼接**：

```
语义：按重要性取 Top-K（几乎恒置）
情景：按相似度 + 新鲜度取 Top-K
合并：一起塞进上下文，用 [偏好] / [历史] 标出来
```

**为什么要打标签**：让模型知道两者的分量不同——偏好是"必须遵守"，历史是"参考"。

### 2.3 打分公式

```
score = 0.60 × 相似度 + 0.25 × 衰减后重要性 + 0.15 × 新鲜度

衰减后重要性 = 原始重要性 × exp(-年龄 / 270天)
新鲜度       = exp(-年龄 / 90天)
```

三个力量在拉扯：

- **相似度**：内容像不像（哈希向量余弦）
- **重要性**：重不重要（写入时打的标）
- **新鲜度**：多久了（指数衰减）

**权重是业务决策，不是技术常数**（§3.3 会给出三种业务的调法）。

### 2.4 遗忘的三种方式

| 方式 | 触发 | 用途 |
|---|---|---|
| **TTL** | 写入时设 `ttl_s`，召回时过滤 | 一次性信息（验证码、临时状态） |
| **显式删除** | `forget(id)` | 用户说"忘掉这件事" |
| **用户级删除** | `forget_user(uid)` | 被遗忘权 / 账号注销 |

**关键点：遗忘必须在"召回"这一层生效**，不能只删库。
因为召回路径可能有缓存、有向量索引副本——**删了主表但索引里还在，等于没删。**

### 2.5 适用范围（边界）

| 场景 | 做法 |
|---|---|
| 同会话多轮 | 4.4 短期记忆就够 |
| 跨会话的用户偏好 | ✅ 语义记忆 |
| 历史工单/历史对话 | ✅ 情景记忆 + 相似度召回 |
| 一次性信息 | ✅ 加 TTL（不加就会污染召回） |
| 需要"精确复现某次对话" | ❌ 这不是记忆，是审计日志 |

### 4.1 记忆条目

```python
@dataclass
class MemoryItem:
    id: str
    kind: str            # semantic / episodic
    text: str
    user_id: str
    created_at: float
    importance: float = 0.5
    ttl_s: float | None = None      # None = 永不过期（但仍会衰减）
    tags: tuple[str, ...] = ()

    def expired(self, now: float) -> bool:
        return self.ttl_s is not None and (now - self.created_at) > self.ttl_s

    def decayed_importance(self, now: float) -> float:
        age = self.age_days(now)
        return self.importance * math.exp(-age / (RECENCY_SCALE_DAYS * 3))
```

### 4.2 召回（含遗忘过滤）

```python
    def recall(self, query, *, user_id, now=None, top_k=3, kinds=None, include_expired=False):
        moment = time.time() if now is None else now
        query_vector = self._embed_sync(query)
        wanted = set(kinds) if kinds else {KIND_SEMANTIC, KIND_EPISODIC}

        scored: list[Recalled] = []
        for item in self._items.values():
            if item.id in self._forgotten or item.user_id != user_id:
                continue
            if item.kind not in wanted:
                continue
            if not include_expired and item.expired(moment):
                continue            # ← 遗忘在这里生效

            similarity = _cosine(query_vector, self._vectors.get(item.id, []))
            importance = item.decayed_importance(moment)
            recency = item.recency(moment)
            score = W_SIMILARITY * similarity + W_IMPORTANCE * importance + W_RECENCY * recency
            scored.append(Recalled(item, score, similarity, importance, recency))
        ...
```

### 4.3 遗忘

```python
    def forget(self, memory_id: str) -> bool:
        """显式删除（被遗忘权 / 用户要求删掉）。"""
        if memory_id not in self._items:
            return False
        self._forgotten.add(memory_id)
        self._items.pop(memory_id, None)
        self._vectors.pop(memory_id, None)
        return True

    def forget_user(self, user_id: str) -> int:
        ids = [item.id for item in self._items.values() if item.user_id == user_id]
        for memory_id in ids:
            self.forget(memory_id)
        return len(ids)
```

## 5. 逐块拆解

### 5.1 为什么打分要三项而不是只用相似度

只用相似度会怎样？实测数据摆在这里：

| 记忆 | 相似度 | 重要性 | 新鲜度 | 总分 |
|---|---|---|---|---|
| 90 天前工单（VPN） | **0.362** | 0.573 | 0.368 | **0.4157** |
| 3 天前偏好（邮件联系） | 0.078 | 0.890 | 0.967 | 0.4143 |
| 30 天前工单（打印机） | 0.067 | 0.358 | 0.717 | 0.2374 |

只看相似度：偏好（0.078）会被打印机工单（0.067）勉强压过，几乎是"随机"的。
加上重要性后，偏好稳稳进前二——这才是对的，**因为它和问题无关但必须遵守**。

### 5.2 90 天前的工单为什么能排第一

因为**相似度权重最高（0.6）**，而它的相似度是 0.362，另两条都不到 0.1。

它虽然旧（新鲜度 0.368，只有 3 天前那条的 38%），
但**内容相关性带来的领先足够大**，压过了新鲜度劣势。

> **这正是我们想要的**："三个月前有过同样的问题"往往比"昨天聊过无关的事"更有用。

### 5.3 0.0014 的差距说明了什么

```
90 天前工单 : 0.4157
3 天前偏好  : 0.4143
差          : 0.0014
```

**冠军只赢了千分之三。** 这意味着：

- 权重从 0.6/0.25/0.15 微调到 0.55/0.30/0.15，冠军就换人
- 年龄从 90 天变成 100 天，冠军也可能换人

**所以这三个权重必须用真实数据调，不能拍脑袋。** 判断标准不是"看起来合理"，
而是**"召回结果对不对"**（这就是阶段五评估要解决的问题）。

### 5.4 为什么 `_embed_sync` 要分两种情况

`HashEmbedder.embed` 是 `async` 的（1.x 为了对接真实 embedding 服务设计的）。
但 `MemoryStore.remember` / `recall` 是同步方法。

```python
    def _embed_sync(self, text: str) -> list[float]:
        import asyncio

        try:
            asyncio.get_running_loop()
        except RuntimeError:
            return asyncio.run(self.embedder.embed([text]))[0]
        # 已在事件循环里：用同步版本
        from servicedesk.rag.embedder import hash_vector

        return hash_vector(text, self.embedder.dim)
```

**为什么不在事件循环里 `asyncio.run`**：会直接抛
`RuntimeError: asyncio.run() cannot be called from a running event loop`（2.6 踩过同一个坑）。

**这是本节的设计妥协**：为了 demo/测试的调用方便，牺牲了一点纯粹性。
生产里应该把整个记忆层做成 async（或注入一个同步 embedder）。

### 5.5 `context_block` 里为什么要写"多少天前"

```
[历史·90 天前] 工单 T-1001：VPN 认证失败，最终通过重置密码解决
[偏好·3 天前] 张伟偏好邮件联系，不喜欢电话打扰
```

**时间信息是给模型推理用的**：同样是"重置密码解决了"，90 天前和 3 天前，
模型该给出的把握程度不同。

**不写时间，模型会把三个月前的解法当成"刚刚发生过"** —— 这是很常见的幻觉来源。

### 5.6 遗忘为什么必须"在召回层生效"

```python
            if not include_expired and item.expired(moment):
                continue
```

如果只在后台任务里删（`forget_expired`），而召回时不检查，会出现两种漏洞：

1. **清理任务还没跑**：过期条目在被删之前一直能被召回
2. **多副本/缓存**：删了主表，向量索引里还在

**双保险**：召回时过滤（正确性）+ 后台清理（省空间）。

## 6. 「故意改坏它」对照实验

### 6.1 实验 A：只用相似度，不看重要性

把权重改成 `1.0/0.0/0.0`：

- 90 天前工单：0.362
- 3 天前偏好：**0.078**
- 30 天前打印机工单：**0.067**

**偏好差点输给一条完全无关的打印机工单。** 而"偏好"是必须遵守的东西——
它消失了，Agent 就可能打电话打扰用户。

### 6.2 实验 B：不做遗忘

把 `expired()` 判断删掉，让所有条目都能召回：

- 那个"临时验证码 123456"（一小时前，TTL 10 分钟）会一直存在
- 问"密码"时它可能被召回 → 模型把**过期验证码**当有效信息

**这不是理论风险**：临时凭证、一次性 token、短期优惠码，全都属于这类。

### 6.3 实验 C：只删主表，不清索引

```python
def forget(self, memory_id):
    self._items.pop(memory_id)       # ← 只删主表
    # self._vectors.pop(memory_id)   # ← 忘了删向量
```

后果：`recall` 遍历 `self._items` 看不到它（因为主表没了），所以**这个 demo 里看不出问题**。
但如果召回是"先向量搜 Top-K，再回主表取内容"，就会拿到空内容甚至报错。

**真实系统里必须两边一起删，或者用"软删除标记"让召回统一过滤。**

## 8. 生产环境踩坑实录

### 坑 1：临时信息污染长期记忆

**现象**

用户问"密码怎么改"，Agent 回了一段"您的验证码是 123456"——那是**一周前**的一次性验证码。

**定位方法**

查召回结果的创建时间：

```python
for row in store.recall(query, user_id=uid, now=now):
    log.info("recall", text=row.item.text[:30], age_days=row.item.age_days(now))
```

`age_days` 很大的条目还在被召回 → 就是这个坑。

**根因**

写入时没设 TTL，召回时也不过滤。

**修法**

- 一次性信息写入时必设 `ttl_s`
- 召回时**永远检查 `expired()`**（§5.6 的双保险）

**顺手加固**：给"未设 TTL 的 episodic 记忆"加一条告警——它大概率是临时信息。

### 坑 2：权重拍脑袋，召回结果反复横跳

**现象**

同一类问题，有时召回旧工单、有时召回偏好，看起来"不稳定"。

**根因**

实测冠军只赢 0.0014（§5.3）。权重稍微一动，排序就变。

**修法**

- 用**有标注的召回评测集**（问题 → 应该召回哪条）来调权重
- 把权重写进配置，别散落在代码里
- 记录每次召回的 score 分解，出问题时能复盘

**顺手加固**：给召回加"分数下限"。低于阈值的干脆不召回——
**召回一条无关的，比什么都不召回更糟。**

### 坑 3：删了记忆，向量库里还在

**现象**

用户要求删除数据后，问他相关问题时仍能召回内容片段。

**根因**

只删主表/关系库，向量索引里的向量没删（或软删除标记没生效）。

**修法**

- 物理删两边，或
- 用**统一过滤**：所有召回路径都必须过 `_forgotten` / `deleted_at` 检查

**顺手加固**：给"删除"写一条端到端测试——**删完之后召回必须为 0 条**
（本节 `test_forget_user_removes_everything` 就是）。

## 9. 自检与作业

### 9.1 三个自检问题

<details>
<summary><b>Q1：语义记忆与情景记忆的检索逻辑有什么不同？</b></summary>

语义记忆（偏好/身份）与当前问题无关但几乎总要带上，按**重要性**取 Top-K；情景记忆（某天发生了什么）按**相似度 + 新鲜度**取 Top-K。合并时打 `[偏好]`/`[历史]` 标签，让模型知道两者分量不同。

</details>

<details>
<summary><b>Q2：为什么 90 天前的工单能排第一？</b></summary>

因为相似度权重最高（0.6），它的相似度 0.362 远高于另两条（0.078 / 0.067）。新鲜度劣势（0.368 vs 0.967）不足以抵消内容相关性的领先。这正是想要的："有过同样问题"比"昨天聊过无关的事"更有用。

</details>

<details>
<summary><b>Q3：遗忘为什么必须在召回层生效，而不只是后台清理？</b></summary>

因为后台清理有延迟（过期到被删之间一直能被召回），而且多副本/向量索引可能不同步。召回时过滤保证**正确性**，后台清理只是**省空间**。两者都要有。

</details>

### 9.2 动手任务：把长期记忆接进 3.x 的图

**要求**

1. 写 `recall_node`：拿用户 ID + 当前问题，召回长期记忆，塞进 `pinned_facts`。
2. 写 `writeback_node`：会话结束时，把"这次怎么解决的"写成一条情景记忆（带 `importance` 与 `ttl_s`）。

**验收标准**

- 新用户（无任何记忆）时，`recall` 返回空列表且不崩。
- 写回的记忆在下一轮能以 `[历史]` 出现。
- 一次性信息（如验证码）写回时 `ttl_s` 不为 None。
- 原有 355 个用例仍全绿。

**提示**：写回时最容易犯的错是"把整段对话原文存进去"——那会让记忆库迅速膨胀，
而且下次召回时全是噪声。存**结论**，不存过程。

## 10. 本节小结与延伸

**三点回顾**

1. **两类记忆检索逻辑不同**：语义按重要性恒置，情景按相似度召回；合并时要打标签。
2. **90 天前的工单排第一**（0.4157），比 3 天前的偏好（0.4143）只高 **0.0014**——**权重必须用评测集调，不能拍脑袋**。
3. **遗忘三件套**：TTL / 显式删除 / 用户级删除；且**必须在召回层生效**（后台清理只省空间）。

**已知限制（诚实记录）**

- **哈希向量不是真语义**：`HashEmbedder` 是字符 n-gram 哈希，同义不同词召回不了（1.7 的局限延续）。
- **无冲突消解**：偏好冲突靠打分排序，可能选错（§9.3）。
- **无持久化**：内存字典，进程停就没了。
- **未接进图**：`recall_node` / `writeback_node` 是 §9.2 作业。
- **无脱敏**：`context_block` 直接拼原文，生产要过滤手机号/身份证（1.4 红线）。
