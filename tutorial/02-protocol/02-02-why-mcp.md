## 1. 为什么需要它（痛点先行）

假设你们公司有三个 AI 应用：**客服助手**、**工单机器人**、**内部 CLI**。
每个都要查资产、查权限、查工单。

**第一个月**，三个应用各自写了一遍 HTTP 调用。没人觉得有问题——每份代码也就 200 行。

**第三个月**，问题来了：

- 资产 API 加了分页，**客服助手改了，另外两个没改**，于是超过 100 条就只拿到第一页
- 权限系统的鉴权方式从 API Key 换成了 OAuth，**三处都要改，改漏了一处**
- 新来的同事问"查资产的超时该设多少"，答案在三个文件里各不相同：3s / 5s / 没设

**这不是代码质量问题，是结构问题。** 同一份能力被实现了 M 次，就会漂移 M 次。

**根因可以写成一个乘法**：

```
每个应用 × 每个系统 = M × N 个适配器
```

M=3、N=2 时是 6 个。看着不多。但 M 和 N 都会增长——**乘法会吃人**。

## 2. 核心概念与架构设计

### 2.1 类比：插头与插座

- **M×N 世界**：每个电器（应用）配一套专用插头，每个插座（系统）形状都不同。你有 5 个电器、5 个插座，就要准备 **25 根转接线**。
- **MCP 世界**：大家统一成一个标准插座。你只需要 **5 个插头 + 5 个插座 = 10 个零件**。

> **这个类比在哪失效**：统一标准要开一次会、写一份规范、所有人学一遍。**这个"协议成本"是真实存在的**——所以当电器只有 1 个时，统一标准纯属浪费。这是本节的量化核心。

### 2.2 两种做法的结构差别

```
做法一：各自定制（M×N）              做法二：统一协议（M+N）
                                    
客服助手 ─┬─ 资产适配                客服助手 ──┐
          ├─ 权限适配                           │
          └─ 工单适配                工单机器人 ──┼─ MCP Client ─┬─ 资产 Server
                                    内部 CLI  ──┘               ├─ 权限 Server
工单机器人 ─┬─ 资产适配（第 2 份）                                └─ 工单 Server
            ├─ 权限适配（第 2 份）
            └─ 工单适配（第 2 份）
```

**注意"第 2 份"这三个字**：它不是"多写一遍"，而是"多一份会独立演化的副本"。

### 2.3 三个角色

| 角色 | 是什么 | 谁负责 |
|---|---|---|
| **Host** | 面向用户的宿主应用，拥有 UI 与最终决策权 | 你 |
| **Client** | Host 内部**为每个 Server** 建立的一条连接 | 协议层/SDK |
| **Server** | 暴露能力的一方，只回答"我能提供什么" | 你或第三方 |

```
┌──────────── Host（你的客服助手）────────────┐
│                                            │
│  Client A ──► Server 资产（远程）           │
│  Client B ──► Server 工单（远程）           │
│  Client C ──► Server 文件（本地子进程）     │
└────────────────────────────────────────────┘
```

**"每个 Server 一条 Client"是关键设计**：每个 Server 的版本、能力、鉴权、生命周期都不同。
拆开之后，一个 Server 挂了不影响其他，一个升级协议不影响其他。

### 2.4 三种原语

| 原语 | 本质 | 谁发起 | 判断口诀 |
|---|---|---|---|
| **Tools** | 动作，可能改变状态 | 模型 | "会不会改变东西？" 会 → Tools |
| **Resources** | 只读数据，按 URI 定位 | Host/应用 | "要不要按标识取一大块只读内容？" → Resources |
| **Prompts** | 预置提示模板 | 用户 | "是不是用户主动挑的一个模板？" → Prompts |

### 2.5 决策四问

| # | 问题 | "否"的含义 |
|---|---|---|
| 1 | 会被**多个**消费方使用吗？ | 只有一个应用用 → 别做 |
| 2 | 需要**独立**部署/升级/鉴权吗？ | 同生共死 → 不必 |
| 3 | 会被**第三方/跨语言**调用吗？ | 只有自己的 Python → 不必 |
| 4 | `M×N > M+N+1` 吗？ | 算数亏 → 先别做 |

### 2.6 适用范围（边界）

| 情况 | 建议 |
|---|---|
| M=1，N 任意 | ❌ 写普通函数 |
| M≥3 且 N≥2 | ✅ 做协议 |
| 跨组织接入 | ✅ 必须做（唯一安全入口） |
| 只是"将来可能复用" | ❌ **等真的出现第二个消费方再做** |

### 4.1 决策核心

```python
PROTOCOL_OVERHEAD = 1   # 协议学习与调试，折算成"几个适配器"


@dataclass(frozen=True)
class Scenario:
    key: str
    title: str
    consumers: int              # M
    systems: int                # N
    needs_isolation: bool = False
    third_party: bool = False


def decide(scenario: Scenario) -> Decision:
    custom = scenario.consumers * scenario.systems
    mcp = scenario.consumers + scenario.systems + PROTOCOL_OVERHEAD
    reasons: list[str] = []

    multi_consumer = scenario.consumers >= 2
    reasons.append(f"问1 消费方 {scenario.consumers} 个 → " + ("✅" if multi_consumer else "❌ 只有自己用"))
    reasons.append("问2 独立部署/鉴权 → " + ("✅" if scenario.needs_isolation else "❌"))
    reasons.append("问3 跨组织/跨语言 → " + ("✅" if scenario.third_party else "❌"))

    arithmetic_win = custom > mcp
    reasons.append(f"问4 适配器 {custom} vs {mcp} → " + ("✅" if arithmetic_win else "❌"))

    # 业务理由优先；算数占优是加分项，不是必需项
    must = scenario.third_party or (scenario.needs_isolation and multi_consumer)
    suggest = must or (arithmetic_win and multi_consumer and scenario.systems >= 1)
    ...
    return Decision(scenario=scenario, suggest=suggest,
                    adapters_custom=custom, adapters_mcp=mcp, reasons=reasons)
```

### 4.2 三个关键判断点

```python
    must = scenario.third_party or (scenario.needs_isolation and multi_consumer)
    suggest = must or (arithmetic_win and multi_consumer and scenario.systems >= 1)
```

- **`third_party` 直接 `must`**：跨组织没有别的选择，协议是唯一能安全暴露能力的方式。
- **`needs_isolation` 还要 `multi_consumer`**：只有一个消费方时，把鉴权做在那个应用里就够了。
- **`arithmetic_win` 还要 `multi_consumer`**：算数上再划算，只有一个消费方也不成立（`M=1` 时 `N > 1+N+1` 永远为假，这条其实是冗余保险）。

## 5. 逐块拆解

### 5.1 为什么 `PROTOCOL_OVERHEAD` 折算成"1 个适配器"

因为要让它和 M×N 在同一量纲上比较。协议成本的真实内容是：读一遍规范、调通握手、处理版本兼容、写一套鉴权。粗略相当于"多写并维护一个适配器"。

**这个常数可以调**：团队已经有 MCP 经验时可以设成 0.5，第一次接触可以设成 2。**关键不是数字精确，而是"你必须把成本算进去"**。

### 5.2 为什么 `M=1` 时算数永远亏

`custom = 1 × N = N`，`mcp = 1 + N + 1 = N + 2`。**永远 `mcp > custom`，差恒为 2。**

这不是巧合：协议的价值来自**复用**。只有一个消费方时，没有任何东西被复用，你只是多了一个进程、一次网络往返、一套鉴权。

### 5.3 为什么 3×2 是"打平"而不是"该做"

`6 vs 6`。纯算数上，做与不做一样多工作量。此时**决策必须由业务理由决定**：

- 需要按角色区分字段（鉴权独立）→ 做
- 三处实现已经在漂移（维护成本高于开发成本）→ 做
- 三个应用其实是同一个团队、同一份代码 → 不做

**"打平"是最难判断的一格**，因为它把决策完全交给了业务。

### 5.4 为什么"跨组织"能压倒算数

场景 C：`2×1 = 2` 个适配器，而协议要 `2+1+1 = 4` 个。**算数上明确更贵，但仍然必须做。**

原因不在数量，在**信任边界**：

- 合作方不能把你的内网 API Key 拿走
- 你得按租户限制他们只能看自己的设备
- 出问题时要能审计"谁在什么时候调了什么"

**这三件事用"发个 Key 让他直接调"是做不到的**——不是成本问题，是安全问题。

### 5.5 三原语的边界为什么必须划清

看一个最常见的误用：把文档做成 Tool。

```python
# ❌ 只读数据做成 Tool
@tool
def get_document(doc_id: str) -> str:
    return DOCS[doc_id]        # 一次返回 4000 字 ≈ 2700 token
```

模型每次回答前都要"决定去读"，读完 2700 token 就进了上下文。**而其中 95% 与问题无关**（1.8 已经证明：无关内容会让模型硬编）。

做成 Resource 则相反：Host 知道有哪些数据可用，可以**按需挂载、按需截断、按权限过滤**，模型只看到它真正需要的部分。

> 口诀：**Tools 是"让模型动手"，Resources 是"让应用铺桌子"。** 铺桌子不该由客人决定。

## 6. 「故意改坏它」对照实验

### 6.1 实验 A：为"将来可能复用"提前上 MCP

假设你有一个"计算 SLA 剩余时间"的函数，只有自己的助手在用。
你决定"反正以后可能有人用，直接做成 MCP Server"。

算一下：

```
M=1, N=0 → 各自定制 = 0 个适配器
          统一协议 = 1 + 0 + 1 = 2 个
          差 = -2
```

**从 0 个适配器变成 2 个（一个 Server + 一个 Client），还附带**：

- 多一个进程要部署、要监控
- 每次调用多一次网络往返（本地 stdio 约 1ms，远程 HTTP 约 20–50ms）
- 多一套鉴权与版本兼容要维护
- 调试从"打断点"变成"抓包看 JSON-RPC"

**收益为零。** 而且真正的成本不在开发，在**后面每一次改动都要同时动 Server 和 Host**。

> 正确顺序（`docs/mcp-notes.md` §6）：**先写函数 → 观察是否出现第二个消费方 → 再抽象。**

### 6.2 实验 B：把只读文档做成 Tool 的 token 账

拿本教程的 `vpn-guide.md` 举例（2588 字符，按 1.6 的 `estimate_tokens` ≈ 1725 token）。

假设：
- 每天 1 万次问答
- 其中 20% 需要查这份文档

| 做法 | 每次注入 | 每天 token | 按 ¥0.3/百万 token |
|---|---|---|---|
| 做成 Tool，每次返回全文 | ≈1725 token | 1万 × 20% × 1725 = **345 万** | **≈ ¥1.04/天** |
| 做成 Resource，按需挂载小节 | ≈150 token（单节） | 30 万 | ≈ ¥0.09/天 |

**差 11 倍。** 而且 Tool 版本还有个副作用：全文进上下文后，模型更容易被无关内容带偏（1.8 §6.2 实测过）。

> 注意：这是**算术估算**，不是实测账单。真实值取决于你的模型单价与实际命中率——但这不影响结论的方向。

## 8. 生产环境踩坑实录

### 坑 1：只有一个消费方就上 MCP

**现象**

团队花了三周做了个 MCP Server，上线后发现只有自己的助手在调。每次改动要同时发两个服务，
本地调试要开三个终端，新人上手先花两天学协议。

**定位方法**

问一句：**"除了我们，还有谁在调？"** 如果答案是"暂时没有"，那就是这个坑。

**根因**

把 MCP 当成"更专业的做法"，而不是"解决 M×N 的手段"。**没有 M×N，就没有要解决的问题。**

**修法**

先把能力写成普通函数（2.1 的 `ToolRegistry` 已经够了），在文档里记一句"若出现第二个消费方，
按 2.4 的流程抽成 Server"。**留下决策记录，比提前实现更有价值。**

### 坑 2：把只读数据做成 Tool

**现象**

账单异常，排查发现某个"查文档"的工具每天被调用几万次，每次返回全文。

**定位方法**

按工具名统计调用次数 × 平均返回 token：

```python
log.info("tool_called", tool=name, result_tokens=len(outcome.content) // 1.5)
```

**根因**

用 Tools 表达"数据"（§5.5）。模型每次都要"决定读不读"，而它倾向于**多读**。

**修法**

- 只读、按 URI 寻址的内容 → 做成 **Resource**，由 Host 决定挂载什么
- 必须留在 Tool 里的话，**限制返回长度**（只返回匹配的段落，不返回全文）

### 坑 3：把业务规则塞进 Prompts

**现象**

"建工单"的必填校验、优先级映射规则，被写进了一个 Prompt 模板。结果模型偶尔漏字段、偶尔把 P1 写成"高"。

**根因**

Prompts 是**给用户点的菜**，不是给程序调用的函数。业务规则放进模板，等于把校验交给自然语言。

**修法**

规则进代码（`pydantic` 模型，见 1.4），Prompts 只负责"话术与结构"。

## 9. 自检与作业

### 9.1 三个自检问题

<details>
<summary><b>Q1：为什么 M=1 时 MCP 永远不划算？</b></summary>

`custom = 1×N = N`，`mcp = 1+N+1 = N+2`，差恒为 2。协议的价值来自复用，只有一个消费方时没有任何东西被复用，你只是多了一个进程、一次网络往返和一套鉴权。

</details>

<details>
<summary><b>Q2：为什么"跨组织"可以让算数结论失效？</b></summary>

因为跨组织的阻碍不是成本而是**信任边界**：对方不能拿你的内网 Key、必须按租户隔离数据、必须能审计。这三件事用"发个 Key 直接调"做不到。此时协议是**唯一可行**的方式，贵也得用。

</details>

<details>
<summary><b>Q3：Tools 和 Resources 的分界线在哪？</b></summary>

**谁决定"用它"**：模型决定 → Tools；应用决定 → Resources。再加一条：**会不会改变状态**——会就必须是 Tools。把只读数据做成 Tool 的代价是模型每次都要"决定读"，既费 token 又不可控（§6.2 实测差 11 倍）。

</details>

### 9.2 动手任务：给自己的项目做一次决策

**要求**

1. 挑出你手上项目里的 **3 个能力**（真实存在的，别编）。
2. 对每个能力填一张表：M=? N=? 是否需独立鉴权？是否跨组织？
3. 跑 `decide()`，把结论和你**直觉的判断**对照。
4. 若结论与你直觉不一致，写一句"为什么"——**这一句才是作业的重点**。

**验收标准**

- 三个能力的 M、N 都有具体依据（能说出"哪三个应用"、"哪两个系统"）。
- 至少有一个能力的结论与你的直觉不同，且你能解释差异来源。
- 把结果追加到 `docs/mcp-notes.md` 的末尾，形成你自己的决策记录。

**提示**：如果你的三个能力都是 `M=1`，那结论很可能是"三个都不该做"——**这不是失败，这是省下了三周**。

### 9.3 拓展挑战

把 `decide()` 从"二值判断"改成"三档建议"：`不做 / 先做函数再说 / 做协议`，并引入"现有实现已漂移程度"作为第五个维度。

**思考**：漂移程度怎么量化？（提示：可以数"同一能力在不同应用里的超时值/重试次数/字段名"有多少种不同取值。）这个指标能自动采集吗？

## 10. 本节小结与延伸

**三点回顾**

1. **MCP 是解决 M×N 的收敛手段**：`M×N` 换 `M+N+1`。`M=1` 时差恒为 2，永远亏。
2. **算数是必要条件，不是充分条件**：跨组织/独立鉴权可以压倒算数（场景 C：`2×1` 明确更贵，但仍然必须做）。
3. **三原语按"谁发起"划分**：Tools 模型发起、Resources 应用发起、Prompts 用户发起。**把只读数据做成 Tool 是最常见、也最贵的误用。**

**已知限制（诚实记录）**

- **`PROTOCOL_OVERHEAD` 是估算值**（取 1）。真实成本取决于团队经验，需要按团队情况调整。
- **未量化"维护成本漂移"**：本节的算数只算"实现数量"，没算"副本独立演化带来的长期成本"。§9.3 的拓展挑战是它的方向。
- **`docs/mcp-notes.md` 里的 token 账是算术估算**，不是实测账单。
